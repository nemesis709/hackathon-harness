# 구현 계획

## 계획의 크기

| 과제 크기 | 계획 형태 |
|---|---|
| 기능 1~2개, 파일 몇 개 | 채팅에 5~10줄. 구현 단위 목록과 첫 번째 확인 명령만 쓴다 |
| 기능 3개 이상, 외부 API·저장소 연동 | 아래 표 형식. 그래도 한 화면 안에서 끝낸다 |

어느 경우든 별도 설계 문서를 만들지 않는다. 남겨야 할 결정만 `notes/decisions.md` 에 적는다.

## 절차

### 1. 실행 환경부터 확인한다

계획을 세우기 전에 제공된 환경이 실제로 도는지 확인한다.

- 언어·런타임 버전, 패키지 관리자, 테스트 러너, 제공된 실행 명령을 확인한다
- 빈 프로그램이나 기존 테스트를 한 번 실행해 출력까지 확인한다. 테스트가 없으면 항상 통과하는 테스트 하나를 만들어 러너가 그것을 찾아 실행하는지(실행 건수 1 이상) 확인한다. `0 tests` 나 대상 없는 `OK` 는 확인으로 치지 않는다
- 이미 설치된 라이브러리와 제공된 스택을 먼저 쓴다. 다른 스택이 필요해 보이면 이유를 붙여 사용자에게 묻는다

### 2. 기능 단위로 나눈다

- 한 단위는 **입력부터 출력까지 한 줄기를 끝까지** 잇는다. "모델 전부 → 서비스 전부 → 화면 전부"처럼 층별로 나누지 않는다
- 한 단위는 한 번에 구현하고 바로 검증할 수 있는 크기다. 30~60분을 넘을 것 같으면 쪼갠다
- 각 단위에 대응하는 요구사항(`R-n`)과 검증 케이스(`V-n`)를 적는다. 대응하는 요구사항이 없는 단위는 만들지 않는다

### 3. 순서를 정한다

1. **가장 단순한 끝-끝 골격**: 입력을 받아 가장 단순한 결과를 내는 것까지 먼저 동작시킨다
2. **Must 기능**: 불확실성이 큰 것(외부 API, 낯선 데이터 형식)을 먼저 한다. 늦게 터지면 고칠 시간이 없다
3. **Should 기능**: Must 가 모두 검증된 뒤에만 시작한다
4. **마지막 30분**: 새 기능을 시작하지 않는다. 전체 재검증, 실행 방법 정리, 설명 준비에 쓴다

### 4. 과설계를 걸러 낸다

계획에 들어간 레이어·추상화·패턴·라이브러리마다 묻는다.

- 지금 요구사항 중 어느 것이 이것을 필요로 하는가?
- 이것을 빼면 어떤 요구사항이 깨지는가?
- 사용자가 이것을 설명할 수 있는가?

답하지 못하면 뺀다. "나중에 확장할 때"는 이유가 되지 않는다.

### 5. 사용자 승인이 필요한 판단을 골라낸다

아래에 해당하는 결정은 AI 가 정하지 않는다. 과제에 해당 항목이 없으면 건너뛴다. 추천안 하나와 대안 하나 이상을 이유와 함께 보여 주고 사용자가 고른다.

- 제공된 스택·환경에서 벗어나는 선택
- 새 외부 의존성 추가
- 데이터 저장 방식(파일·메모리·DB)과 스키마
- 요구사항을 두 가지로 읽을 수 있는 부분의 해석
- Must 범위를 줄이는 결정

## 출력 형식 (기능 3개 이상일 때)

```markdown
## 구현 계획
환경: <런타임·버전>, 실행 `<명령>`, 테스트 `<명령>` (확인함: <출력 요약>)

| # | 단위 | 요구사항 | 검증 | 비고 |
|---|---|---|---|---|
| 0 | 끝-끝 골격 | — | `<명령>` 이 <결과> 를 출력 | |
| 1 | ... | R-1 | V-1, V-2 | 불확실: API 응답 형식 |

승인 필요: <결정 목록과 추천안>
```

## 결정 기록 기준

`notes/decisions.md` 에는 다음 중 하나에 해당하는 결정만 남긴다.

- 되돌리기 어렵다 (저장 방식, 데이터 형식, 핵심 라이브러리)
- 맥락 없이 보면 "왜 이렇게 했지?" 하고 물을 만하다 (평가자가 물어볼 만한 선택)
- 실제로 대안을 비교해 골랐다
- 범위를 줄였다 (Must·Should 를 빼거나 미뤘다)

넷 중 어디에도 해당하지 않으면 기록하지 않는다. 형식을 채우려고 결정을 만들지 않는다.
