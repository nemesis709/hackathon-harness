# 검증과 리뷰

## 원칙

- **자기 보고를 믿지 않는다.** "테스트 통과했습니다"라는 말이 아니라 실행한 명령과 출력이 근거다. 구현한 AI 와 같은 세션이라도 명령은 이 단계에서 다시 실행한다.
- **모든 판정은 셋 중 하나로 끝난다.** 통과, 실패, `검증 불가`. 실행해 보지 못한 것을 통과로 쓰지 않는다.
- **지적 수를 채우지 않는다.** 볼 것이 없으면 0건이 정답이다. 취향 차이는 SUGGESTION 으로만 낸다.
- **모든 지적에는 위치(파일:라인), 문제, 수정안, 근거가 있다.**

## 기능 하나마다 도는 루프

```
1. 게이트      실행·테스트·(있으면) lint·타입체크를 직접 실행
2. 요구사항 대조  해당 기능의 V-n 을 하나씩 실행해 기대 결과와 비교
3. 리뷰        세 관점(요구사항·위험·과설계)을 한 번씩 본다
4. 수정        BLOCKER·WARNING 만 고친다 → 1번부터 다시
```

- 게이트가 깨진 코드는 리뷰하지 않는다. 먼저 고친다.
- 같은 문제를 **두 번 고쳐도 실패하면** 멈춘다. 아래 「오류 원인 찾기」의 전체 절차로 가거나, 사용자에게 범위 축소를 제안한다.
- 기능마다 `notes/verification.md` 에 남기는 것은 두 가지다: 실행 기록 한 줄(명령과 출력 요약), 해당 `V-n` 의 상태. 리뷰 지적과 오류 표는 지적·오류가 있을 때만 행을 추가한다. 없으면 실행 기록에 "리뷰 지적 없음"이라고 쓴다.

## 리뷰 관점 (각 한 번)

과제에 해당하지 않는 항목(예: 사용자 구분이 없는데 R3)은 하나씩 따지지 않고 `N/A: R3, R5` 처럼 한 줄로 묶는다.

### 요구사항 — 약속한 것을 만들었나

| # | 확인 |
|---|---|
| S1 | Must 기능의 `V-n` 이 모두 실제로 실행되어 통과했는가 |
| S2 | 업무 규칙과 예외(`notes/requirements.md` 규칙 표)가 코드에 반영됐는가. 경계값(0, 빈 값, 중복, 최대값)에서 정해진 대로 동작하는가 |
| S3 | 테스트가 동작을 확인하는가. 호출만 하고 결과를 단언하지 않는 테스트, 테스트 대상까지 mock 으로 바꾼 테스트는 통과로 치지 않는다 |
| S4 | 오류 입력에서 프로그램이 죽지 않고 정해진 방식(거부·경고·기록)으로 처리하는가 |

### 위험 — 실패하면 무엇이 망가지나

| # | 확인 |
|---|---|
| R1 | 비밀값(API 키·토큰·비밀번호)이 코드·로그·기록 파일에 들어가지 않았는가 |
| R2 | 외부 입력을 검증하는가. 쿼리·명령·경로에 입력을 그대로 이어 붙이지 않는가(인젝션, 경로 탈출) |
| R3 | 권한: 다른 사용자의 데이터를 id 만 바꿔 읽거나 고칠 수 없는가 (사용자 구분이 있을 때) |
| R4 | 개인정보가 로그·에러 메시지·출력으로 새지 않는가 |
| R5 | 같은 요청이 두 번 오거나 중간에 실패해도 데이터가 어긋나지 않는가 (쓰기가 여러 단계일 때) |
| R6 | 데이터를 지우거나 덮어쓰는 동작이 되돌릴 수 있거나, 사용자 확인을 거치는가 |
| R7 | 크기 제한 없이 전체를 읽거나 반복하는 곳이 과제의 데이터 규모에서 문제가 되지 않는가 |

### 과설계 — 필요 없는 것을 만들었나

| # | 확인 |
|---|---|
| O1 | 요구사항 어디에도 없는 기능·옵션·설정이 들어갔는가 |
| O2 | 구현이 하나뿐인 인터페이스, 한 번만 쓰는 헬퍼, 빈 레이어가 있는가 |
| O3 | 승인받지 않은 의존성이 추가됐는가 |
| O4 | 사용자가 설명할 수 없는 코드가 있는가. 있으면 단순하게 다시 쓰거나 사용자가 읽어야 할 위치로 표시한다 |
| O5 | 디버그 출력, 주석 처리된 코드, 임시 파일이 남았는가 |

## 심각도

| 등급 | 기준 | 처리 |
|---|---|---|
| BLOCKER | 요구사항 위반, 버그, 보안·데이터 위험, 거짓으로 통과하는 테스트 | 반드시 고치고 다시 검증 |
| WARNING | 경계 사례 누락, 과설계, 설명하기 어려운 구조 | 고친다. 시간이 없으면 한계로 기록 |
| SUGGESTION | 개선 제안, 취향 | 고치지 않고 기록만 한다 |

## 오류 원인 찾기

오류의 복잡도에 따라 절차를 다르게 쓴다.

| 오류 | 처리 |
|---|---|
| 원인이 에러 메시지에 그대로 드러난다 (오타, import 누락, 문법 오류, 타입 불일치, 잘못된 경로) | 바로 고치고 같은 명령으로 다시 실행한다. 실행 기록 한 줄이면 충분하다 |
| 원인이 불명확하다, 두 번 고쳐도 실패한다, 가끔만 재현된다, 출력이 조용히 틀린다 | 아래 전체 절차를 따른다 |

전체 절차에서는 코드를 바로 고치지 않고 아래 순서를 따른다.

1. **재현 루프를 만든다.** 버그를 빠르고 매번 똑같이 보여 주는 명령이나 실패 테스트 하나를 만든다. 재현되지 않으면 가설로 넘어가지 않는다.
2. **증상을 정확히 적는다.** 에러 메시지, 잘못된 출력, 기대값을 그대로 옮긴다.
3. **가설을 2~3개 세운다.** "X 가 원인이면 Y 를 바꿨을 때 사라진다" 형태로 쓴다. 가설이 하나뿐이면 첫 생각에 갇힌다.
4. **한 번에 하나만 바꿔 확인한다.** 디버그 출력에는 공통 표식(예: `[DBG]`)을 붙여 나중에 한 번에 지운다.
5. **고친 뒤 재현 명령을 다시 돌린다.** 가능하면 그 재현을 회귀 테스트로 남긴다.
6. **정리한다.** `[DBG]` 출력을 지우고, 맞았던 원인을 `notes/verification.md` 에 한 줄 적는다.

## 완료 판정

아래가 모두 참일 때만 "완료"라고 말한다. 하나라도 거짓이면 무엇이 남았는지 함께 보고한다.

- [ ] Must 기능의 `V-n` 이 모두 통과 (명령과 출력이 기록됨)
- [ ] 게이트(실행·테스트) 통과
- [ ] open BLOCKER 0건
- [ ] 미구현·미검증 항목이 `notes/verification.md` 에 적혀 있음

## 제출 직전 1회

- 깨끗한 상태에서 과제 결과물의 실행 방법(과제가 요구한 형식, 또는 결과물 README)에 적힌 명령 그대로 처음부터 실행한다. 실행 방법 문서가 없으면 만들고, 명령이 문서와 다르면 문서를 고친다.
- 전체 테스트를 한 번 더 돌리고 결과를 기록한다.
- 세 관점 리뷰를 전체 변경에 대해 한 번 더 본다. 도구가 별도 컨텍스트의 리뷰어(서브에이전트 등)를 지원하면 이 단계에서만 한 번 써도 된다. 구현 맥락이 없는 시선이 놓친 문제를 잡는다. 리뷰어에게는 결론이 아니라 요구사항 파일과 코드 위치를 넘긴다.
