# 설명과 인계

목적은 그럴듯한 설명문이 아니라 **사용자가 자기 말로 설명할 수 있게 되는 것**이다.

## 근거 규칙

- 모든 주장에 근거를 붙인다. 근거는 셋 중 하나다.
  - 코드 위치 `파일:라인`
  - 실행 기록 `notes/verification.md` 의 항목, 또는 지금 다시 실행한 명령과 출력
  - 결정 기록 `notes/decisions.md` 의 `D-n`, 요구사항 `notes/requirements.md` 의 `R-n`·`V-n`
- 근거를 찾지 못한 주장은 쓰지 않는다. 꼭 필요하면 `확인 안 됨` 을 붙인다.
- 코드에 없는 동작, 실행하지 않은 테스트, 기록에 없는 결정 이유를 만들어 내지 않는다. 결정 이유가 기록에 없으면 사용자에게 묻는다.
- 성능·안정성 같은 성질은 측정한 경우에만 수치로 쓴다.

## 절차

1. **구조를 코드에서 뽑는다.** 파일 목록, 진입점, 입력에서 출력까지 데이터가 지나가는 경로를 실제 코드를 읽고 정리한다. 기억이나 계획에 의존하지 않는다. 계획과 실제가 다르면 실제를 쓴다.
2. **결정을 모은다.** `notes/decisions.md` 에서 결정, 이유, 버린 대안을 가져온다.
3. **범위를 대조한다.** `notes/requirements.md` 의 Must·Should·Won't 를 하나씩 보고 구현됨·부분 구현·미구현으로 표시한다.
4. **검증 결과를 가져온다.** `notes/verification.md` 에서 통과·실패·`검증 불가` 를 그대로 옮긴다.
5. **한계를 적는다.** 테스트하지 않은 입력, 승인된 가정, 남은 WARNING, 데이터 규모가 커졌을 때 깨질 수 있는 곳을 적는다.

## 출력 형식

`notes/explanation.md` 에 쓴다. 과제가 설명 문서를 다른 이름·위치로 요구하면 그것을 따른다.

```markdown
# <결과물 이름> 설명

## 한 문단 요약
누가 무엇을 하려고 쓰는가, 무엇을 입력받아 무엇을 내놓는가.

## 구조
- 진입점: `<파일:라인>`
- 흐름: 입력 → <처리 단계> → 출력 (각 단계에 파일:라인)

## 주요 결정
| 결정 | 이유 | 버린 대안과 이유 | 근거 |
|---|---|---|---|

## 구현 범위
| 요구사항 | 상태 | 근거 |
|---|---|---|
| R-1 (Must) | 구현됨 | V-1 통과 (verification #3) |
| R-4 (Should) | 미구현 | 시간 부족으로 제외 (D-3) |

## 검증 결과
실행 명령, 결과, 날짜·시각. 실패하거나 검증하지 못한 항목도 그대로 적는다.

## 알려진 한계와 실패 가능성
- <조건> 에서 <무엇이> 잘못될 수 있다. 근거: <파일:라인 또는 테스트 부재>
```

## 이해도 점검

설명 초안을 만든 뒤 사용자에게 질문 5~8개를 던진다. 평가자가 물어볼 만한 질문이다.

- 이 구조를 고른 이유와 버린 대안은 무엇인가
- 입력 X 가 들어오면 어떤 경로를 지나 어떤 결과가 나오는가 (파일 이름으로)
- 규칙 R-n 의 예외는 어디서 처리하는가
- 이 테스트는 무엇을 보장하고, 무엇을 보장하지 못하는가
- 데이터가 100배가 되면 어디가 먼저 문제가 되는가
- 시간이 더 있었다면 무엇을 먼저 고치겠는가

진행 방식:

1. AI 는 질문만 먼저 내고 사용자 답을 기다린다. 모범 답안을 먼저 보여 주지 않으며, 사용자 대신 답하지 않는다. 사용자가 없는 자동 실행이면 질문 목록만 `notes/explanation.md` 끝에 남긴다.
2. 사용자가 답하면 AI 는 코드와 기록에 비추어 맞는지, 빠진 것이 있는지 근거와 함께 알려 준다.
3. 사용자가 답하지 못한 부분은 읽어야 할 코드 위치를 알려 준다. 그래도 설명하기 어려운 코드라면 단순하게 다시 쓰는 것을 제안한다.
