# 요구사항 발견

## 역할 분담

- **사람(사용자)** 이 담당자에게 묻고, 받은 답을 그대로 전달한다.
- **AI** 는 다음에 물을 질문과 그 이유를 제안하고, 답을 `notes/requirements.md` 에 정리한다.
- AI 는 담당자의 답을 추측해서 채우지 않는다. 답이 없는 칸은 아래 상태 중 하나로 둔다.

| 상태 | 뜻 | 다음 행동 |
|---|---|---|
| `미정` | 아직 묻지 않았거나 답을 기다린다 | 담당자에게 묻는다 |
| `[가정]` | 담당자가 모르거나 "알아서" 라고 했다. AI 가 기본값을 제안했다 | 사용자에게 승인받는다 |
| `[가정-승인]` | 사용자가 그 기본값을 승인했다 | 확정으로 취급하고, 설명 단계에서 가정이었다고 밝힌다 |

담당자가 "알아서 정해 주세요" 라고 답하면 AI 는 가장 단순한 기본값 하나를 이유와 함께 제안하고, 해당 규칙·입력 행에 `[가정]` 으로 적는다. 사용자가 승인하면 `[가정-승인]` 으로 바꾼다.

## 진행 규칙

1. **먼저 직접 확인한다.** 과제 설명, 제공된 코드·데이터·API 문서로 답할 수 있는 것은 묻지 않고 읽어서 확인한다. 확인한 사실은 출처와 함께 적는다.
2. **한 번에 1~3개만 묻는다.** 질문마다 "왜 묻는지"와 "답에 따라 구현이 어떻게 달라지는지"를 한 줄로 붙인다. 답이 구현을 바꾸지 않는 질문은 하지 않는다.
3. **질문에 추천 답을 붙인다.** 담당자가 "그걸로 해 주세요"라고 빠르게 답할 수 있게 한다. 단, 추천 답은 확정이 아니다.
4. **용어를 맞춘다.** 같은 말이 두 가지로 읽히면(예: "사용자"가 고객인지 운영자인지) 정의를 묻고 `용어` 칸에 적는다.
5. **모순을 드러낸다.** 담당자의 말이 과제 문서·데이터와 다르면 둘을 나란히 보여 주고 어느 쪽이 맞는지 묻는다.

## 질문 흐름

아래 다섯 단계를 순서대로 지나가되, 각 단계의 분기는 답에 따라 고른다. 이미 답이 있는 단계는 건너뛴다.

### 1. 업무와 문제

시작 질문: "누가, 어떤 상황에서, 지금 어떻게 처리하고 있고, 무엇이 문제인가요?"

| 답이 이렇다면 | 다음 질문 |
|---|---|
| 지금 사람이 손으로 처리한다 | 그 절차를 단계별로 말해 달라. 가장 오래 걸리거나 실수가 잦은 단계는 어디인가 |
| 기존 시스템이 있다 | 그 시스템에서 무엇을 그대로 두고 무엇을 바꾸는가. 기존 데이터·화면과 호환이 필요한가 |
| 사용자가 여러 역할이다 | 역할별로 볼 수 있는 것과 할 수 있는 것이 다른가 |
| 문제가 추상적이다("불편하다", "느리다") | 최근 실제 사례 하나를 들어 달라. 그때 무엇을 원했는가 |

### 2. 입력 데이터와 제공 API

시작 질문: "어떤 데이터가 들어오고, 어디서 받으며, 결과는 어디로 가나요? 샘플이 있나요?"

| 답이 이렇다면 | 다음 질문 |
|---|---|
| 파일(CSV·JSON 등)이다 | 샘플을 받는다. 크기, 인코딩, 결측·중복·잘못된 값이 있을 때 처리 방법 |
| 외부·제공 API 다 | 인증 방식, 응답 예시, 실패 응답, 호출 제한. 실제로 한 번 호출해 확인할 수 있는가 |
| DB·기존 저장소다 | 읽기만 하는가, 쓰기도 하는가. 스키마를 바꿔도 되는가 |
| 샘플이 없다 | 형식을 가정해 예시를 만들어 보여 주고 승인받는다. 승인 전에는 `가정` 으로 표시한다 |

### 3. 업무 규칙과 예외

규칙 하나마다 경계 사례로 확인한다. "정확히 마감 시각에 들어온 건은?", "같은 요청이 두 번 오면?", "값이 0 이거나 비어 있으면?"

| 답이 이렇다면 | 다음 질문 |
|---|---|
| 규칙끼리 충돌할 수 있다 | 어느 규칙이 우선인가 |
| 규칙을 어긴 입력이 있다 | 거부하는가, 경고만 하는가, 기록하고 넘어가는가 |
| 돈·개인정보·삭제가 관련된다 | 되돌릴 수 있어야 하는가. 누가 할 수 있는가. 기록을 남겨야 하는가 |
| "보통은 ~합니다"라고 답한다 | 보통이 아닌 경우는 어떤 것이 있고, 그때는 어떻게 하는가 |

### 4. 우선순위와 MVP

시작 질문: "오늘 하나만 동작한다면 무엇이어야 하나요?"

- 기능을 **Must / Should / Won't** 로 나눈다. Must 는 남은 시간의 절반 안에 끝낼 수 있는 양으로 줄인다. 나머지 시간은 검증과 수정에 쓴다.
- Won't 에는 "이번에 하지 않는 것"과 이유를 적는다. 담당자가 기대했는데 빠진 기능이 나중에 드러나는 일을 막는다.
- UI·성능·배포 형태 같은 비기능 요구도 여기서 확인한다. 묻지 않으면 가장 단순한 형태(예: CLI, 로컬 실행)로 가정하고 승인받는다.

### 5. 성공 조건과 검증 기준

시작 질문: "무엇을 보면 '됐다'고 판단하시겠어요?"

- Must 기능마다 **입력 예시와 기대 결과 한 쌍 이상**을 받는다. 이것이 검증 케이스 `V-n` 이 된다.
- 담당자가 예시를 주지 못하면 AI 가 예시를 만들어 보여 주고 맞는지 확인받는다.
- "잘 동작하면 된다" 같은 답은 측정할 수 있는 형태로 다시 묻는다.

## 종료 신호

다음이 모두 참이면 발견을 멈추고 구현 계획으로 넘어간다.

- [ ] Must 기능마다 검증 케이스 `V-n` 이 하나 이상 있다
- [ ] 입력 형식이 샘플이나 승인된 가정으로 정해졌다
- [ ] 돈·개인정보·삭제·권한과 관련된 규칙에 `미정`·`[가정]` 이 남지 않았다 (`[가정-승인]` 은 괜찮다)
- [ ] 남은 `미정`·`[가정]` 은 Must 구현을 막지 않는다

질문을 끝없이 이어 가지 않는다. 구현 중에 새 질문이 생기면 그때 다시 이 절차로 돌아온다.

## 출력

`notes/requirements.md` 를 채운다 (형식은 하네스의 `templates/requirements.md`). 담당자에게 확인받은 것과 AI·사용자가 가정한 것을 구분해서 적는다.
